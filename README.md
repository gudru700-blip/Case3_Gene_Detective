# СИНТЕЗ: анализ генетических вариантов и фенотипов

Документация к файлам:
- `final_code_sintez_local.py` — основной последовательный сценарий;
- `prepare_stage1.py` — подготовка VCF и HPO;
- `check_top3_genes.py` — отбор трёх генов и дополнительные проверки.

## Назначение

Программа сопоставляет генетические варианты с фенотипическими признаками случая, добавляет аннотации Ensembl VEP, частоты gnomAD и сведения ClinVar, формирует список генов-кандидатов и итоговую таблицу.

Это исследовательский учебный конвейер. HPO-совпадение — доля совпавших признаков, а не вероятность заболевания. Итоговый вердикт обозначает кандидата для проверки; причинность варианта автоматически не устанавливается.

## Файлы проекта

 1. Gene_detective.py
 2. prepare_stage1.py 
 3. check_top3_genes.py 
Требуемые исходные данные: папка или ZIP-архив с файлами `case_XX*.vcf` / `case_XX*.vcf.gz` и `case_XX*phenotype*.json`. Поиск рекурсивный. Для каждого случая должны существовать оба файла. Идентификатор случая извлекается из пути по шаблону `case_\d+`.

Поддерживаются однонуклеотидные замены SNV. Многоаллельная запись разделяется на отдельные строки ALT. Исходный GT сохраняется; для каждого ALT определяется состояние носительства.

Пример файла фенотипов:

```json
{
  "phenotypicFeatures": [
    {"type": {"id": "HP:0001250", "label": "Seizure"}, "excluded": false},
    {"type": {"id": "HP:0001263"}, "excluded": true}
  ]
}
```

`excluded: true` означает отсутствие признака. Один HPO-код не должен одновременно быть присутствующим и отсутствующим.

## Архитектура

Архитектура файловая: этапы обмениваются TSV и JSON на диске. База данных и отдельный сервер не используются. Основной файл выполняется сверху вниз; часть функций и словарей остаётся в памяти для пересчёта фенотипов.

Номер этапа в основном сценарии отличается от номера каталога результатов:

| Этап сценария | Действие | Результат |
|---|---|---|
| 1 | Выбор папки или распаковка ZIP | data_dir и ROOT |
| 2 | Вызов prepare_stage1.py; разбор VCF и фенотипов | stage1_results |
| 3 | Аннотация уникальных SNV через Ensembl VEP | stage2_results |
| 4 | Частоты из ответа VEP и точные совпадения ClinVar | stage3_results |
| 5 | Сопоставление заболеваний с HPO и сортировка кандидатов | stage4_results/phenotype_candidates.tsv |
| 6 | Проверка ClinVar XML, аллеля и записей RCV | Дополненные файлы stage4_results |
| 7 | Вывод топ-3 с присоединением частот по variant_id | Таблицы на экране |
| 8 | Применение порогового правила HPO | stage5_results/final_verdicts.tsv |
| 9 | Ввод дополнительных признаков выбранного случая | case_XX_top3_updated.tsv и case_XX_verdict_updated.tsv |

### Основные выходные файлы

| Каталог | Файлы и назначение |

Ключ варианта: `chrCHROM:POS:REF:ALT`, например `chr15:48412568:C:A`. Частоты присоединяются именно по `variant_id`.

### Кэширование и ошибки

Ответы VEP сохраняются пакетами; подпись кэша зависит от входных вариантов, параметров и URL. Скачанный ClinVar VCF используется повторно. XML ClinVar и ответы дополнительных проверок также кэшируются.

Для части запросов предусмотрены повторные попытки и задержки. Ошибки ClinVar XML записываются в отдельную таблицу. Статус ошибки загрузки или отсутствие записи не равнозначны отсутствию биологической связи.

## Методы расчёта

### HPO

Используется точное совпадение кодов с аннотациями заболевания. Семантическая близость и распространение по родительским узлам HPO не рассчитываются. Отдельно учитываются совпадения с отсутствующими признаками.

На этапе 5 кандидаты сортируются по `matched_count`, затем по `frequency_total`. Неизвестная частота помещается после известных при равном числе совпадений.

### Частоты gnomAD

Общая частота извлекается из ответа VEP для соответствующего ALT и позиции:
1. `gnomadg` — приоритетный источник;
2. `gnomade` — если первый отсутствует.

Учитывается общая частота, если не известно этническое происхождение пациента. Разные значения одного источника отмечаются как конфликт; неизвестная частота не заменяется нулём.

`frequency_total_percent = frequency_total × 100`.

Это частота аллеля в выбранной выборке, а не вероятность болезни. 

### Топ-3 в текущем check_top3_genes.py

Определение 3 наиболее вероятных генов-кандидатов определяется по совокупнсоти критериев: фенотипическому попаданию, частоте, статусу патогенности, функциональное знаечние замены, доброкачественности/злокачественности.

### Правило итогового вердикта

- При наличии HPO > 0.9 выбирается один кандидат с наименьшим gene_rank; остальные не выводятся.
- Если таких кандидатов нет, выводятся гены с HPO от 0.3 до 0.9 включительно.
- Гены с HPO < 0.3 не перечисляются.
- Если подходящих генов нет, выводится сообщение, что кандидаты не выделены.

Пороговое правило принято для этого проекта. Оно не доказывает моногенную причину или совместное участие нескольких генов.

### Дополнительные признаки

Пользователь выбирает case_XX или его номер, затем вводит HPO через пробел, запятую или точку с запятой. Проверяются формат и конфликт с отсутствующими признаками.

Пересчитываются только три ранее выбранных гена. Новый ген за пределами прежнего топ-3 не появится. После пересчёта сортировка идёт по числу совпадений и частоте.

## Ограничения

- Сборка GRCh38 предполагается на входе; REF не сверяется с FASTA.
- VEP вызывается для всех подготовленных уникальных вариантов: предварительного отбора только фенотипически подходящих генов в этих файлах нет.
- У одной мутации могут быть последствия для нескольких транскриптов; это создаёт несколько строк аннотаций.
- Высокое HPO-сходство, публикация и запись в базе по отдельности не подтверждают диагноз.
